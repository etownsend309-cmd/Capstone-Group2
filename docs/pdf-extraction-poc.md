# PDF extraction proof of concept — KAN-402

**Status:** experiment complete, recommendation provisional
**Scope:** evaluation only. This is not the capstone application.

## 1. Objective

The capstone assumes it can read text out of vendor agreement PDFs. This ticket
tests that assumption before anything is built on it, and answers three
questions:

1. How well does PDF.js extract text from a contract PDF?
2. What does it do with a PDF it cannot read?
3. When should the team stop trying and ask for supplied plaintext instead?

A fourth question turned out to matter more than expected, so it is answered
here too: **how do we know the extracted text is in the right order?**

## 2. Library under test

| | |
| --- | --- |
| Library | PDF.js, via the `pdfjs-dist` npm package |
| Version tested | **6.3.289** |
| Build used | `pdfjs-dist/legacy/build/pdf.mjs` |
| Recorded license | Apache-2.0, as declared in the package metadata |

Two notes on the version:

- **The `legacy` build is used in both the browser and the Node scripts.** The
  modern build calls `Promise.try`, which Node 22 does not implement, so the
  benchmark would have measured a different code path than the app. One build
  removes that discrepancy.
- **6.3.289 was chosen for a security reason.** Version 5.7.284 was the first
  one installed, and `npm audit` reported GHSA-hq66-cqwq-w95j against the range
  `>=5.6.83 <6.2.108`: a high-severity flaw allowing arbitrary JavaScript
  execution when opening a malicious PDF. A tool whose entire purpose is opening
  PDFs the team did not author cannot ship on an affected version. `npm audit`
  now reports 0 vulnerabilities.

The license above is what the package records. The team must verify license
compatibility before making a production selection; that is not decided here.

## 3. Test fixtures

Every fixture is synthetic, generated by `npm run fixtures`, and committed. The
contract text is fictional; the parties ("Northwind Analytics, LLC" and "Blue
Harbor Logistics, Inc.") do not exist. No real agreement is in this repository.

The generator is TypeScript (`scripts/generateFixtures.ts`) using `pdf-lib` for
PDF authoring and `jimp` to raster text for the scanned fixture.

| Fixture | Category | What it is | Built to prove |
| --- | --- | --- | --- |
| `clean-agreement.pdf` | clean | 2-page single-column services agreement, Helvetica, normal text layer | The good case works |
| `multicolumn-agreement.pdf` | difficult | 2-page two-column terms, **content stream written in visual row order** | Reading order can break while character count looks perfect |
| `scanned-agreement.pdf` | scanned | 1-page image-only addendum, rendered from known text to a grayscale JPEG | Unusable extraction is recognised, not silently accepted |
| `corrupt-agreement.pdf` | unknown | Damaged body and cross-reference table | Failure is visible |

Each extractable fixture ships an `.expected.txt` file containing the exact text
that was drawn, in correct reading order. That is genuine ground truth — it is
the generator's input, not a transcription of the output — which is what makes
the reading-order measurement in §5 possible.

## 4. The two extraction strategies

Both strategies consume **one** PDF.js parse of the document. They compare two
ways of reconstructing text from the same text items.

**This is not a comparison of two PDF engines.** It is a comparison of two
reconstruction approaches over identical PDF.js output. Any difference between
them is attributable to the reconstruction, not to the parser.

### Strategy A — content-stream order (`src/pdf/contentOrder.ts`)

Concatenate PDF.js text items in the order the PDF's content stream lists them,
breaking a line wherever PDF.js sets its end-of-line marker. About ten lines of
code. This is what you get by default from the obvious `getTextContent()` loop.

### Strategy B — coordinate reconstruction (`src/pdf/coordinateOrder.ts`)

Ignore stream order and rebuild reading order from geometry:

1. Drop empty items and sort everything by descending `y`.
2. Group items into lines: same line if their baselines are within 60% of the
   text height. Sort each line left to right by `x`.
3. Look for a column gutter — a vertical band in the middle 25–75% of the page
   that almost no line crosses. Occupancy is measured per line across 600 bins,
   and up to 15% of lines (or at least one) may cross it, so a centred
   full-width heading does not hide the gutter. The band must be at least 1.2%
   of the text width; see §5.4 for why that number matters more than it looks.
4. If a gutter is found, emit the left column top-to-bottom, then the right
   column. A line that genuinely spans the gutter (a heading) flushes the
   buffered columns first, so it appears where it belongs.
5. Within a line, insert a space where the geometric gap between two items
   exceeds 20% of the text height.

This is an experiment, kept deliberately readable, not a production layout
engine. Its documented limitations: one gutter per page, no paragraph rejoining
across line breaks, tables lose their structure, rotated text interleaves, and
footnotes are emitted in page position rather than reference position.

## 5. Results

Measured by `npm run benchmark`. Full output in
[`artifacts/pdf-benchmark-results.md`](../artifacts/pdf-benchmark-results.md);
nothing below is hand-written.

Environment: pdfjs-dist 6.3.289, Node v22.22.2, darwin/arm64, 3 repeats per
fixture with the fastest reported. Figures below are from the run generated at
2026-09-28T18:18:03Z; re-running the benchmark overwrites the artifact.

### 5.1 Quality

Two ground-truth measures, both order-sensitive in different ways:

- **Coverage** — order-independent token recall. "Did we get all the words?"
- **Order** — longest-common-subsequence ratio against ground truth. "Are they
  in the right sequence?"

A high coverage with a much lower order score is exactly the signature of a
reading-order failure, and the harness flags it when the gap exceeds 15 points.

| Fixture | Strategy | Printable chars | Coverage | Order | Reading order suspect |
| --- | --- | --- | --- | --- | --- |
| `clean-agreement.pdf` | A — content order | 3,269 | 100.0% | 100.0% | no |
| `clean-agreement.pdf` | B — coordinate | 3,269 | 100.0% | 100.0% | no |
| `multicolumn-agreement.pdf` | A — content order | 1,339 | 100.0% | **60.6%** | **yes** |
| `multicolumn-agreement.pdf` | B — coordinate | 1,339 | 100.0% | 100.0% | no |

**This is the central finding of the ticket.** On the multi-column fixture both
strategies returned *byte-for-byte identical character counts* — 1,339 printable
characters, 100% token coverage, zero empty pages. By every volume metric they
are indistinguishable. Yet Strategy A's reading order scores 60.6% and Strategy
B's scores 100%, because Strategy A interleaves the two columns:

```
Strategy A:  A. DEFINITIONS B. SERVICE LEVELS
             "Authorized User" means an employee or Provider targets monthly availability of
             contractor of Customer permitted to access the ninety-nine and five tenths percent (99.5%)

Strategy B:  A. DEFINITIONS
             "Authorized User" means an employee or
             contractor of Customer permitted to access the
             ...
             B. SERVICE LEVELS
             Provider targets monthly availability of
```

Strategy A's output is not merely untidy. Clauses from two unrelated sections
are spliced into single sentences. Any downstream consumer — a human reader, a
search index, a model — would be reading text that does not exist in the
document.

The practical consequence: **character count cannot be used to judge extraction
quality.** Any future "did extraction work?" check that counts characters would
have passed this document with full marks.

On the clean single-column fixture the two strategies agree exactly, so
Strategy B costs nothing on easy documents.

### 5.2 Latency

| Fixture | Pages | Total | Strategy A reconstruct | Strategy B reconstruct |
| --- | --- | --- | --- | --- |
| `clean-agreement.pdf` | 2 | 6.00 ms | 0.01 ms | 0.43 ms |
| `multicolumn-agreement.pdf` | 2 | 3.15 ms | <0.01 ms | 0.21 ms |
| `scanned-agreement.pdf` | 1 | 31.62 ms | 0 ms | 0 ms |
| `corrupt-agreement.pdf` | 1 | 0.52 ms | 0 ms | 0 ms |

Reconstruction is not the cost; parsing is. Strategy A is close to free at about
0.01 ms, and Strategy B costs 0.2–0.45 ms per document — under 10% of total
time. The scanned fixture is the slowest overall because PDF.js decodes a JPEG
and then finds no text.

The character counts and quality scores above are stable across runs; these
latency figures move by roughly 10–20% run to run, so treat them as an order of
magnitude rather than exact values. They are also small fixtures on a fast
machine: a realistic 40-page agreement has not been measured.

### 5.3 Failure handling

| Fixture | Status | Printable chars | Fallback | Behaved as designed |
| --- | --- | --- | --- | --- |
| `clean-agreement.pdf` | success | 3,269 | not needed | yes |
| `multicolumn-agreement.pdf` | success | 1,339 | not needed | yes |
| `scanned-agreement.pdf` | **failed** | 0 | recommended | yes |
| `corrupt-agreement.pdf` | **failed** | 0 | recommended | yes |

All four fixtures matched their declared expectation.

## 5.4 Validation against an external corpus

After the synthetic fixtures passed, the harness was run against
[`py-pdf/sample-files`](https://github.com/py-pdf/sample-files) — 35 public
CC-BY-SA PDFs built specifically to break PDF parsers. They are not committed
here; point the benchmark at a local checkout:

```bash
npm run benchmark -- --fixtures-dir /path/to/sample-files --out-dir artifacts/local
```

All 35 parsed without crashing the harness, and every one produced a defensible
status:

| Behaviour | Count | Notes |
| --- | --- | --- |
| Clean success | 15 | Includes PDF/A, Google Docs, pdfkit, ReportLab, LaTeX |
| Warning | 11 | Mostly the low-text heuristic on small or image-heavy pages |
| Failed — image-only | 6 | Correctly identified as scanned; fallback offered |
| Failed — password | 1 | Correct `password-protected` reason and message |
| Failed — unparseable | 1 | `Invalid Root reference`, reported as a damaged PDF |
| Crashes or hangs | **0** | |

Three results are worth recording specifically.

**It found a real bug in Strategy B.** `026-latex-multicolumn/multicolumn.pdf`
is a genuine two-column LaTeX document. Strategy B failed to detect its gutter
and interleaved the columns — the exact fault Strategy B exists to prevent —
while Strategy A, which happened to match LaTeX's authoring order, was correct.
The cause was that `minGutterRatio` had been set to 3.5% of the text width,
tuned against our own synthetic fixture, whose gutter is wide. LaTeX's default
`\columnsep` of 10pt is about **1.7%** of a 467pt text width, so every real
two-column document fell under the threshold. The threshold is now 1.2% and the
occupancy scan runs at 600 bins to resolve it. The safeguard against false
positives is not the band's width but the requirement that almost no line
crosses it — a gap between words is clear on one line, not on forty.

Re-running the whole corpus after the fix changed Strategy B on **0 of 117**
pages of the 117-page `GeoTopo.pdf` and 0 pages of every other document, so the
narrower threshold introduced no false gutters.

The lesson generalises beyond the one constant: **a layout heuristic tuned only
against fixtures you generated yourself will encode your generator's habits.**
The synthetic multi-column fixture was deliberately pathological, and passing it
gave false confidence about the ordinary case.

**A 117-page document is fine.** `GeoTopo.pdf` extracted 110,317 printable
characters from 117 pages in **625 ms**, with Strategy B's reconstruction
accounting for 22 ms of it. This partly answers the capacity question in §11:
the cost is roughly 5 ms per page and scales linearly, so a 40-page agreement
should be well under a second.

**Password protection is handled correctly.** `005-libreoffice-writer-password`
returns `failed` with reasons `password-protected` and `extraction-error`, and
the message "This PDF is password protected. The proof of concept does not
accept passwords, so its text cannot be read." No stack trace reaches the
interface.

Two documents still show large A/B divergence, and neither is a defect: the
ReportLab overlay file draws three lines in an order that does not match their
vertical position, so A gives authoring order and B gives visual order; and on
`029-optional-content-groups` (a layered map) B is clearly better, rendering the
scale bar as `0 50 100 200 Miles` where A merges it into `20050`.

## 6. Failure modes and how each is surfaced

The core invariant, enforced in `src/pdf/evaluateExtraction.ts` and covered by
unit tests: **a run with zero printable characters is never reported as a
success.** Status is `failed` when there was a fatal error, zero pages, or zero
printable characters; `warning` when a fallback rule or page-level problem
fired; `success` only otherwise.

| Condition | Status | What the tester sees |
| --- | --- | --- |
| Scanned / image-only | failed | Named reason `scanned-no-text-layer`, and an explanation that PDF.js does not perform OCR |
| Empty output | failed | `all-pages-empty`, plus the per-page character counts |
| Whitespace-only output | failed | `whitespace-only`; whitespace is not counted as text anywhere |
| Some pages empty | warning | `summary-empty` count and the explicit list of empty page numbers |
| Corrupt / invalid PDF | failed | "PDF.js could not parse this file. It is not a valid PDF, or its structure is damaged." |
| Password-protected | failed | `password-protected`, and a statement that the POC does not accept passwords |
| Unsupported file type | blocked before parsing | `"<name>" is not a PDF. This proof of concept only accepts .pdf files.` |
| Empty or oversized file | blocked before parsing | Byte count, and the 25 MB limit |
| Suspiciously low text volume | warning | `low-text-volume`, labelled as a heuristic |
| PDF.js exception | failed | One short sentence, mapped by exception type |
| Timeout (30 s budget) | failed | `extraction-timeout` |

**Raw stack traces are never shown.** `describeError` maps each PDF.js exception
to one plain sentence. Developer detail goes to `console.debug` only, and a
component test asserts the interface contains neither `    at ` nor `.mjs:`.

One benign warning is worth recording because it appears in the benchmark
output: PDF.js logs `Ensure that the standardFontDataUrl API parameter is
provided` for the fixtures using Helvetica. That parameter supplies glyph
outlines for *rendering*. This POC never renders a page, and text extraction was
100% accurate without it, so it is not wired up.

## 7. Scanned PDF behaviour

The scanned fixture was rendered from text we know exactly, then flattened to a
grayscale JPEG. PDF.js returned **0 printable characters from 1 page**, as it
should.

What matters is that the harness distinguishes *scanned* from *broken*. It
inspects each page's operator list for `paintImageXObject`,
`paintInlineImageXObject`, and `paintImageMaskXObject`. A page with images but
no text is a scan; a page with neither is corrupt or empty. The two get
different reasons and different messages:

- scanned → `scanned-no-text-layer`: "Pages carry images but no text layer …
  PDF.js reads existing text and does not perform OCR, so supplied plaintext is
  the only path here."
- neither → "No text layer and no page images were found. The document may be
  corrupt, empty, or use an unsupported construction."

That distinction was worth building: an early version labelled the *corrupt*
fixture as "scanned", which would have sent a tester looking for OCR to solve a
file-corruption problem.

**This POC does not make scanned extraction succeed, and is not intended to.**
It recognises unusable extraction, says so explicitly, and offers the plaintext
fallback.

## 8. The plaintext fallback decision

### When it is offered

Any of: PDF.js failed outright; the document is unreadable or
password-protected; zero pages; every page empty; whitespace-only output; text
volume below the documented threshold; a scanned document with no text layer;
timeout; or a reviewer ticking "mark this extraction unusable".

### The threshold

`LOW_TEXT_THRESHOLD_PER_PAGE = 50` printable characters per page, averaged
across the document.

**This is a POC heuristic, not a confidence score.** It is a character count
with a round number attached. It carries no probability and no model output, and
50 was chosen because a page of a real agreement carries thousands of
characters, so anything near 50 is a fragment rather than a page of text. It is
labelled as a heuristic everywhere it appears: in the interface masthead, in the
exported report's caveats, and in the benchmark header.

One calibration data point from §5.4: 11 of the 35 corpus documents tripped it.
Every one was a genuinely tiny document — a one-line test file, a form, a map
label — rather than a failed extraction, which is the right call for those files
but a reminder that on a corpus of small documents this rule fires often. A
contract corpus should almost never trip it, and if it does, the threshold is
wrong rather than the documents.

### Switching sources

**The source never changes silently.** The panel shows the active source as a
banner. A tester pastes text or uploads a `.txt` file, and the banner still
reads "PDF extraction (PDF.js)" until they press **Confirm use of supplied
plaintext**. Only then does it change to "Supplied plaintext (pasted)" or
"(uploaded)", with a confirmation timestamp and a character count, and the
change is announced in the live region. It can be reverted.

Whitespace-only supplied text cannot be confirmed — the button stays disabled
and the panel says so. Both behaviours are covered by tests.

## 9. OCR research note

**No OCR was added, and no OCR dependency was installed.** Recording what is
known, for whoever picks up that decision:

1. **PDF.js does not perform OCR and is not going to.** It reads a PDF's
   existing text layer. This is not a gap in our usage; it is the boundary of
   what the library does.
2. **A scanned agreement contains no extractable text at all.** Our scanned
   fixture yields exactly 0 characters. No amount of tuning the reconstruction
   changes that, because there is nothing to reconstruct. OCR is not an
   optimisation of this work; it is a different technology.
3. **OCR needs its own evaluation.** It introduces questions this ticket did not
   ask: per-character accuracy on contract typography, language and font
   coverage, bundle size (a browser OCR engine plus its trained data is
   typically tens of megabytes), runtime cost, whether processing stays on the
   client, and how OCR confidence is surfaced without implying more certainty
   than exists.
4. **JavaScript OCR options exist and can be evaluated in a separate ticket.**
   Tesseract.js and Scribe.js are the usual client-side candidates. Neither was
   installed or benchmarked here, so this document makes no claim about how well
   either performs. That comparison is the deliverable of the follow-up ticket.
5. **The MVP can ship without OCR.** The supplied-plaintext fallback already
   covers the scanned case: the tester is told extraction is unusable, and can
   supply the text. That is a workable path until an OCR approach is approved.

## 10. Provisional recommendation

Provisional. It rests on four synthetic fixtures and no production documents.

1. **PDF.js is adequate for machine-generated agreement PDFs.** 100% token
   coverage and 100% reading order on the clean fixture, in single-digit
   milliseconds, entirely client-side.

2. **Use coordinate-based reconstruction, not content-stream order.** It matches
   Strategy A exactly on easy documents and is the only one of the two that
   reads the multi-column document correctly. The cost is under half a
   millisecond per document, under 10% of total time. Content-stream order is
   cheaper but produces spliced clauses on multi-column layouts while reporting
   identical character counts, which makes it the more dangerous default. Note
   that the present implementation handles one gutter and would need hardening
   for tables and more complex layouts.

3. **Keep processing on the client.** It worked for every fixture, it removes a
   whole class of privacy problem, and it means no contract ever leaves the
   machine.

4. **Require an explicit plaintext fallback path in the MVP.** Scanned
   agreements exist and will produce nothing. The product needs a defined answer
   before that first happens, not after.

5. **Do not use character count as an extraction-quality gate.** The
   multi-column fixture is the counter-example: full marks on volume, badly
   wrong on order. If a quality check is needed, it has to consider order.

7. **Validate any layout heuristic against documents you did not create.** The
   gutter bug in §5.4 passed every one of our own fixtures and failed the first
   real two-column PDF it met. Whatever ships should be run against an external
   corpus before it is trusted.

Then, separately:

8. **Treat OCR as a separate, scoped decision** (§9).

## 11. Remaining questions

- **How does this behave on a real agreement?** The fixtures are synthetic and
  the external corpus in §5.4 is technical rather than contractual. A 30–60 page
  PDF from an actual vendor, with tables, signature blocks, and exhibits, is the
  obvious next test. `fixtures/private/` exists for exactly that and is
  git-ignored.
- **How common are multi-column contracts in our corpus?** This drives how much
  the Strategy B decision actually matters.
- **What about tables?** Neither strategy reconstructs a table. Agreement
  pricing schedules and SLA tables are usually tables. This is untested and
  probably the largest gap.
- **What happens with a 200-page PDF?** Partly answered: 117 pages took 625 ms
  in Node (§5.4), so the 30-second timeout has ample headroom. Untested in the
  browser, where the work runs in a worker but the result is still held in
  memory in the tab.
- **What accuracy does the product actually need?** "100% coverage" on a
  synthetic fixture does not tell us the tolerance for a document whose clauses
  carry legal weight.
- **Is the 50-character threshold right?** It has never been calibrated against
  a real document. It is a starting point to be replaced by something measured.
- **How should extraction quality be checked in production?** §5.1 establishes
  that counting characters is insufficient. What replaces it is an open
  question, since ground truth will not exist at runtime.
- **Password-protected agreements:** currently a hard failure. Whether the
  product should accept a password is a product decision, not a technical one.

## 12. Reproducing this

```bash
npm install
npm run fixtures     # regenerate the test PDFs
npm run benchmark    # rewrite artifacts/pdf-benchmark-results.{json,md}
npm test             # unit and component tests
npm run test:e2e     # Playwright browser tests
npm run dev          # the evaluation UI
```

No Python, no backend, no network access, and no API keys are involved. See the
root [`README.md`](../README.md) for the full command list and the privacy rules.
